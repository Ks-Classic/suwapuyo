### 残課題（軽量対応）
- **M-1 Issue ID一本化**: Gate=`FL-G##`, Event=`FL-E##` に統一。TODOの関連リンクは番号付き正式体系へ差し替え。
- **M-2 2台連結**: MVPは**1台横長(1枚)を正**と明記。2台連結は拡張表示・ベゼル・性能再測定が要る別検証に分離。
- **M-4 性能定量**: FPS閾値(12〜20体≥50fps / 30体≥30fps)、マーカー切り出し成功率(例:30枚中良好18+)を合格基準化。

### iPad実装で先に銀行に積む注意（Gate前提）
1. カメラ経路は**標準Safariタブ**(standalone PWA不可)。
2. Canvasは**DPR上限2・Undo浅め・破棄時 `canvas.width=0`**(iOSのCanvasメモリ上限~384MB回避)。
3. `touch-action:none` ＋ 非ズームviewport ＋ リスナーは `{passive:false}`。

## B. 3日Gate実装計画（2026-06-25判定に向けた歩く骨格）

> 原則: きれいなUIではなく「最もリスクの高い縦の一本」を最短貫通し、判定を**実測の証拠**で出す。装飾・凝った演出・AIはGate後。
> **同期はGateから本番同一構成（スマホ→Supabase→表示）で実装**（単一PCで作ると本番にもテストにもならないため・D-4更新）。Supabase未接続時のみ単一PC/IndexedDBでローカルフォールバック実証。FL-G01は `SupabaseArtworkRepository`(正本)＋IndexedDBキャッシュ、FL-G04は Realtime購読で反映。

### Day 1 — データ＆入力
- **FL-G01** Supabase(Storage/Postgres/Realtime)＋IndexedDB Blobキャッシュ(`idb`)、`persist()`、DB sequence採番、`storage.estimate()`確認
- **FL-G02** 紙撮影パス: スマホ標準カメラ入力 or `getUserMedia` → **自前マーカー検出**＋ホモグラフィ → official安定時は自動プレビュー → 連結背景透過 → Storage登録
- **FL-G03** 最小デジタルキャンバス(素Canvas、ブラシ＋パレット＋Undo＋**透過PNG出力**)＝Gate実証＆フォールバック

### Day 2 — 表示ワールド＆操作
- **FL-G04** PixiJS ふわふわワールド: 8〜30体・ふわふわ移動・ランダム/主役/非表示/全リセット
- **FL-G05** 下の名前ラベル(任意)＋スタッフの**ID/名前ジャンプ検索**(M-3)
- **FL-G06** **計測オーバーレイ**(FPS/メモリ/作品数/容量)(D-8)

### Day 3 — 検証＆判定
- **FL-G07** 6時間ソーク: 300枚・60分以上・10秒毎入替・途中でリセット/指定/非表示・**ログ取得**(D-6)
- **FL-G08** スタッフ1人10作品連続登録(平均60秒以内)＋DELL視認性(1台横長)
- **FL-G09** **判定レポート記入** → Go / Conditional Go / No-Go

### Go / Conditional Go / No-Go（D-2/D-6/D-9反映）
- **Go**: 塗り絵台紙またはデジタル描画の登録→表示成立 / 12〜20体安定(FPS基準) / リセット・ランダム・指定・非表示・復旧OK / 1人運用見通し / マーカー切り出し＋連結背景透過が実用水準。
- **Conditional Go**: マーカー切り出しや透過が不安定でも**そのままカード表示orデジタル入力で成立** / Supabaseは成立するが当日ネット不安時の運用手順を追加すれば成立。
- **No-Go**: 12体で停止 / 登録平均2分超 / 復旧不能 / ソークでメモリ破綻。
