AI壁打ちの境界「どういう人に刺さるか」の初期ブレストはAIに相談OK・有効。だが心理的動線＝「本当に何が刺さるか」の神髄はAIだとろくな結果にならない、センスが要る、人間の判断。design-os（全agentに境界として明記）

競合は後（順番）先にPRFAQで価値を定義→次に競合。どのレベルまで磨けば意味があるかを逆算。過密市場はラインが上がる、空白領域は存在自体が価値。design-strategy / prfaq-evaluator
デザインプリンシプルスローガンでなく「何を優先するか」の宣言。横槍（PM/上司/エンジニア/マーケ）に流されず裁定する軸。「ユーザー第一」＝スローガン（無効）。「速さ vs 機能性では速さ」＝戦略（有効）。優先順位が具体的でないと使えない。design-strategy / design-principle-referee
開く前の3点①誰のために ②どこまでやれば価値 ③プリンシプル。この3つが自分の言葉で固まると後の作業が完全に変わる。design-strategy（Gate 0 合格基準）
02 — 分類ルール

skill か、agent か、壁打ちか、評価か

これが「これらはなにエージェントになるか？」への核心の答え。判断基準を一文で言うと——

原則 · 動画③から導出

判断・神髄・意思決定は SKILL（人間がメインスレッドで回す手順）に残す。
AGENT は判断を奪わず、選択肢を広げる（壁打ち）か、客観基準で減点する（評価）だけ。

根拠：動画③が明言する「刺さるかの神髄はAIに任せるとろくな結果にならない／センスが要る／人間がやるべき判断」。一方で「初期ブレストの壁打ちはAI有効」。この二つを同時に満たす唯一の設計が、判断はskillで人間に残し、agentは発散と採点に限定すること。

SKILL にするもの

方法論・テンプレート・ゲート基準・チェックリスト・アンチパターン警告。メインスレッドで人間と対話しながら順番に回すもの。3動画の知見の大半（手順と判断）はここ。skillは「人間に正しい問いを、正しい順番で突きつける」。

AGENT にするもの

独立した文脈と敵対的スタンスが効くものだけ。本体の文脈を汚さず並列で走り、結論だけ返す。2種：
・壁打ち＝発散。選択肢/仮説を広げ凡庸さを叩く。決定はしない。
・評価＝収束。客観基準で減点・監査する。「並べた瞬間気持ち悪い」を自動化。

やってはいけない設計

「誰に刺さるか／どの感情を狙うか」を agentに最終決定させない。そこを自動化した瞬間、動画③が警告する凡庸化が起きる。壁打ちagentは必ず「候補・仮説を返すが、選ぶのは人間」と振る舞う。これを全agentの定義に boundary として焼き込む。

Agents — 壁打ち（発散） · Extended

target-sharpener

壁打ち

曖昧な対象・「みんなのため」を検出し尖らせる。刺さる相手の候補を発散（動画③が明示的にAI可とした領域）。凡庸さ警報。選ぶのは人間。

desire-digger

壁打ち

わらしべ長者式に「その先に何を？」を反復し、根の欲望まで掘る。手段（金/時間/承認）と本質を分離。仮説を返すのみ。

Agents — 評価（採点・監査） · ★consistency-auditor のみ Core

consistency-auditor ★

評価 · Core

最も"評価エージェント"らしい一つ。プロトタイプ/画面/CSSを design.md と突き合わせ、色ズレ・余白・4の倍数違反・radius不一致・コントラスト割れを機械的に検出。「並べた瞬間気持ち悪い」の自動化。

prfaq-evaluator

評価

PRFAQを採点：価値ラインが明確か／スコープが有界か／感動が具体か／制約スタートになっていないか。

emotion-journey-critic

評価

4ステージjourneyを監査：全ステージ埋まっているか／結果が感情で終わるか／知る・アクセスの混同／尺・文脈整合。

design-principle-referee

評価

横槍・トレードオフ衝突時にプリンシプルを適用して裁定。スローガン原則（「ユーザー第一」）を無効と弾く。

Core / Extended の線引き

Core（5つ）＝3 skills ＋ design-os ＋ consistency-auditor。これだけで「上流の9割」を体系化し、唯一機械化できる評価（一貫性）を持つ。Extended（5つ）＝壁打ち2＋評価3。実運用で「ここが手薄」と分かってから足す。最初から10個作るのはYAGNI。

05 — ふわふわランド 実適用

机上の空論にしない

同じパイプラインを、実在する すーすーわーわー ふわふわランド（YourTIME 2026-08-02）に通す。既存docには要件・アーキ・テストは厚いが、この上流3層がほぼ空白だった。ここを埋めるのが実価値。

Gate 0 — 戦略

誰のため（一文・尖らせる）

主役は二者いるが、感情設計は子ども一点に絞る（動画③：尖らせろ）。親とスタッフは"制約条件"として扱う。

成功の一文「YourTIMEに来た5〜9歳の子どもが、自分が塗った絵が大画面のふわふわ世界で生きて泳いでいるのを見つけ、親に『見て！あれ私の！』と叫ぶ。」
＝言葉と行動で定義された成功。これに寄与しないものは全部後回し。

欲望チェーン（わらしべ長者・desire-digger）

子ども：自分の絵が動く→自分が作ったものが世界に認められた→承認・万能感→「自分は特別だと感じたい・見てもらいたい」
親：子の笑顔・作品が残る→いい時間を過ごせた・創造性を伸ばせた→「子に良いものを与えている安心」

→ 口腔育成は親の欲望（子の健康）経由で、遊びの中に接続。説教にしない（成功条件「押しつけにならない」と一致）。

どこまでやれば価値（PRFAQ・プレスリリース ドラフト）

Press Release（未来の発表文）本日、YourTIME会場に「すーすーわーわー ふわふわランド」が登場。子どもが塗り絵で描いたキャラクターが、その場で大画面のふわふわ世界へ飛び込み泳ぎ出します。子どもは自分の絵をすぐ見つけ「私の絵が動いてる！」と歓声。親子の会話が生まれ、遊びの延長で鼻呼吸・口腔育成にやさしく触れられます。

価値ライン＝「塗る→その場で登場→自分の絵を見つける→歓声」が成立すれば勝ち。AIコメント/AI動画/SNS自動投稿はGate後。
👉 これは既存 01_project-overview.md の「MVPでやらないこと」と完全一致＝この案件は無自覚にPRFAQ的スコープ切りが出来ていた（良い兆候）。

競合（順番：PRFAQの後）

参加型「塗り絵→その場でデジタル展示」は直接競合が薄い空白領域。動画③：空白領域は質ラインが低くても成立、存在自体が価値。→ 過剰作り込み不要、薄く速いGate方針が戦略的に正しい。逆に汎用お絵かきアプリ（過密）と戦ってはいけない。

#プリンシプル（A > B）裁定できる横槍の例

Gate 1 — UX文脈（4ステージ × 2アクター）

子ども（感情の主役）

①知るDISCOVER
遠くから見える大画面のふわふわ世界と塗り絵台、他の子の歓声→「何あれやりたい」。入り口を太く：画面を会場の目線に、台紙の存在を明快に。
②アクセスACCESS
台紙＋クレヨンで塗る（主）／タブレットの最小キャンバス（フォールバック）。文脈＝会場で立ったまま・親と・短時間→短時間で塗れる線画・握りやすさ。
③使うUSE
スタッフ撮影→数秒で自分のキャラが登場→自分の絵を探して見つける。核＝登場の瞬間＋探索。実装上は FuwafuwaWorld / featured / secretMode がこの層。
④結果EMOTION
「自分の絵が世界で生きてた」＝誇り・万能感、親に見せる。残るもの＝記憶＋台紙のお土産。作り手側結果（口コミ／満足度／認知／SNS素材）は全部この感情の後についてくる。

スタッフ（運用の成否＝制約条件だが感情も設計対象）

③使うUSE
撮影→マーカー切り出し→60秒で登録、リセット/指定/非表示。タップ数最小（自動プレビューD-10）。
④結果EMOTION
「詰まらず回せた・自分一人でも運用できた」安心。これも設計対象（運用成功条件）。
この設計から出る判断

感情ピーク＝「自分の絵を初めて見つける登場の瞬間」。→ 実装リソースをここに集中せよという設計判断が機械的に出る。現状の実装はここ専用の演出（初回ハイライト／登場サウンド／親の視線誘導）が要件化されていない（→ §06）。

06 — 実装レビュー所見

実装も見た（約3700行の実体）

React 19 ＋ PixiJS 8 ＋ Supabase ＋ IndexedDB。store / capture / renderer の分離は綺麗。ただしエンジニアリング先行で上流を飛ばした症状が見える＝動画群の警告そのもの。

良い（残す）

  • store/capture/renderer の責務分離が明確
  • 視覚的な値が config.ts に集約され始めている（トークン化の素地）
  • レスポンシブ／safe-area／touch-action 対応済
  • 計測オーバーレイ（FPS/メモリ/容量）＝Gate判定の実測証拠（D-8）
  • 「MVPでやらないこと」が明確＝無自覚なPRFAQスコープ切り

retrofit ギャップ（このOSが埋める）

  • design.md / tokens.css が無い。視覚決定がCSS/configに散在し実害（radius 22 vs 8 不一致）
  • フォント未設計（system-ui）＝ブランドDNA未注入
  • 感情ピーク「登場の瞬間」が要件化されていない（featuredはあるが「自分の絵を初めて見つける」専用演出が無い）
  • ジャーニーが暗黙（子ども/スタッフ別の4ステージが文書化されていない）
consistency-auditor を今走らせたら出る指摘（デモ）

config.card.cornerRadius:22 が CSS の border-radius:8px と矛盾 ／ radius が 2/6/8/999 で散在しキーライン未定義 ／ フォントがブランド未設計 ／ spacing が clamp() で非トークン化。——これらが動画①の言う「並べた瞬間に気持ち悪い」候補。retrofitで回収可能だが、すでにCSSに焼かれた分の手直しコストは残る（→ §08 懸念2）。

08 — 懸念

遠慮なく、7つ

  1. AIに任せてはいけない境界（最重要）。動画③が明言「刺さるかの神髄はAIだとろくな結果にならない」。だから壁打ち/評価agentは"発散と減点"に限定し、「誰に刺さるか／どの感情か」の最終決定は人間（木幡さん/クライアント）に残す設計にした。ここを破ってagentに決めさせると凡庸化する。→ 全agentに boundary を焼き込む。
  2. 後付け retrofit の限界。ふわふわランドは実装3700行が先行。design.mdを後から作っても、すでにCSSに焼かれた決定（radius不一致等）の手直しコストが残る。→ ふわふわは「retrofitの実例」として価値があるが、本来の順序効果は次の新規案件から得る。
  3. 過剰エンジニアリング（CR-4 / KISS / YAGNI）。10コンポーネントは多い。→ Core 5つ（3 skills＋orchestrator＋consistency-auditor）から始め、効果が出てからExtendedへ。CLAUDE.md「管理コスト>価値なら提案しない」に従う。
  4. ゲート規律が形骸化しやすい。「早く作りたい」圧で上流を飛ばすのが人間の常（ふわふわが実例）。→ orchestratorに未通過で進ませない強制力を。ただし強すぎると鬱陶しい→0→1とPMF後でゲート厳しさを変える（CLAUDE.mdのフェーズ認識と整合）。
  5. 「自分のための製品」も凡庸さの罠。このOS自体を"全クライアント汎用"に広げすぎると、動画③の警告通りぼやける。→ まず木幡さんの実案件という尖った文脈に最適化する。
  6. Claude Design 依存。動画①の実演はClaude Design前提。design.mdは標準規格でツール非依存だが、プロトタイプ工程はツール選択が残る。→ skillはツール非依存で書く（動画①の「不変の真理」に従う）。来年ツールが変わっても順番は変えない。
  7. 二者ユーザーの綱引き。ふわふわは子ども（感情）とスタッフ（運用）が利益相反しうる（演出を凝る＝タップ増）。→ プリンシプルで優先順位を固定し、Gate1で両者を別ジャーニーとして可視化した。現場で揺れたらプリンシプルに立ち戻る。
