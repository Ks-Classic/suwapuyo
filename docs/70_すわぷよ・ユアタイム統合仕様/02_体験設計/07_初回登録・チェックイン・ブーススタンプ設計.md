# 初回登録・チェックイン・ブーススタンプ設計

> 状態: デモ設計。DB migration・本番配信は別Gate  
> 最終更新: 2026-07-13（公式アカウントをホームとする単一LIFF・作品QR入口を反映）
> 目的: 初回入力の負荷を抑えながら、イベント来場とブース体験を本人の明示操作で記録し、遊び・キャラクター・出展者価値へ還元する

## 1. 体験原則

1. 最初に価値を伝え、必要な情報だけをその場で聞く。
2. 1画面1判断を基本にし、長い説明を読ませない。
3. 保存前に取得項目と利用目的を短く正直に示す。
4. チェックインやブース訪問はGPSで推測せず、QR読取または明示操作を証跡にする。
5. 報酬は読取直後に付与し、アンケートを報酬の条件にしない。
6. `訪問した`と`説明を聞いた／体験した／購入した`を混同しない。
7. 利用者には自分の履歴、出展者には安全な集計、運営には全体ファネルを返す。
8. デモはローカル／仮データでも成立させ、本番のイベントモデルへ置換できる境界を保つ。
9. 通常入口と再訪先はLINE公式アカウントのリッチメニューへ統一し、LIFFを独立した入口として意識させない。
10. 作品固有QRは同じLIFFのclaim routeへ入り、受取後に公式アカウントの通常導線へ合流する。

## 2. 初回登録の最短フロー

```text
公式アカウントのリッチメニューからすわぷよを開く
  ↓
単一LIFF起動・必要時のLINE認可・友だち状態確認
  ↓
利用目的の確認（1画面）
  ↓
だれが遊ぶ？
  ├─ 大人だけ → すぐゲーム
  └─ 子どもが遊ぶ
        ↓
      何人遊ぶ？（1〜4／5人以上）
        ↓
      子どもごとの年月・性別
        ↓
      登録人数の最終確認
  ↓
キャラクター4枠を自動編成
  ↓
最初のゲーム
```

初回にチュートリアル、興味カテゴリ、流入元、通知設定、体操種別を聞かない。必要になった瞬間に文脈内で案内する。

## 3. 画面仕様

### 3.1 利用目的

- 見出し: `みんなで遊びやすくするために`
- 本文: `遊ぶお子さんの生まれた年月、性別、遊んだ記録を保存します。年齢に合わせた表示、サービスの改善、利用傾向の集計と分析に使います。`
- 補足: `登録した情報は、あとから確認・変更・削除できます。`
- 主CTA: `内容を確認してはじめる`
- 副CTA: `今はやめておく`
- 常設リンク: `利用規約`、`プライバシーポリシー`

### 3.2 遊ぶ人

- 見出し: `今日はだれが遊ぶ？`
- 選択肢: `子ども`、`子どもと大人`、`大人`
- 説明は選択後に出し、選択前の文章量を増やさない。
- `大人`では子ども情報を聞かない。

### 3.3 人数

- 見出し: `遊ぶお子さんは何人？`
- 1〜4を大きな数値ボタン、`5人以上`は追加操作とする。
- 既定値を勝手に確定しない。1タップで次へ進む。
- 戻って人数を減らす場合、削除対象を明示して確認する。

### 3.4 子どもの情報

- 見出し: `1人目のお子さん`
- 進捗: `1 / 3`のように残り人数を示す。
- 項目: `生まれた年`、`月`、`性別`
- 年・月はモバイル向けpicker。未来月と対象外年月は選択肢から除く。
- 性別候補: `女の子`、`男の子`、`その他`、`答えたくない`。値と表示ラベルは分離する。
- CTA: 最終以外は`次のお子さんへ`、最終は`確認する`。
- 1人分を保存する前に全員分を端末上のdraftとして保持し、最終確定で一括保存する。
- 中断時のdraft保持期間と同意前保存の境界は詳細設計で固定する。

### 3.5 確認

- 見出し: `○人で遊ぶ準備ができたよ`
- 各人は`1人目・2020年5月・女の子`のように一覧表示する。
- 各行に`変更`を置く。
- 主CTA: `すわぷよで遊ぶ`
- 保存成功後だけゲームへ遷移する。失敗時は入力を失わず再試行できる。

### 3.6 作品QRからの初回入口

```text
作品登録成功
  ↓
作品固有QRを読む
  ↓
/claim/{opaque_token}
  ↓
LINEログイン・ID tokenのサーバー検証
  ↓
受取対象のキャラを確認
  ↓
利用目的確認・友だち追加
  ↓
claim確定
  ↓
このキャラで遊ぶ
  ↓
次回はLINE公式アカウントのリッチメニューから再訪
```

- 作品QRは公式アカウントQRに代わる恒常ホームではなく、個別作品を受け取る一時入口とする。
- QRには作品ID、LINE user ID、氏名を載せず、サーバー解決用のopaque tokenだけを載せる。
- 受取対象を表示してから確定し、QRを開いただけではclaimしない。
- tokenは一回限り、期限付き、失効可能、冪等とする。転送、誤読取、紛失、再発行を扱う。
- 親のLINEアカウントで複数の子ども・複数作品を管理できる設計を保つ。
- 本番schema、署名、RLS、復旧運用はGate通過前に実装しない。

## 4. イベントチェックイン

### 4.1 目的

- すわぷよ利用者のYourTIME.来場を、本人の明示操作で確認する。
- 来場の喜びを即時報酬へ変え、会場回遊と再プレイを促す。
- イベント前のプレイ、当日の来場、イベント後の継続を同じ利用者の許可された範囲で分析する。

### 4.2 利用者フロー

```text
会場入口のQRを読む
  ↓
LIFFの /event/{campaign}/check-in を開く
  ↓
イベント名・日付を確認
  ↓
[会場にチェックイン]
  ↓
即時成功演出
「YourTIME.へようこそ！」
  ↓
当日限定キャラクター登場
  ↓
[すわぷよで遊ぶ] [ブースを見つける]
```

- QRを開いただけではチェックインを確定せず、イベント名を見た上でボタンを押す。
- 同じ利用者・同じcampaignの重複チェックインは冪等に成功扱いとする。
- 報酬付与は一度だけ。再読取では`チェックイン済み`と次の行動を表示する。
- 当日限定キャラクターは開催期間、再利用可否、イベント後の扱いをcampaign設定で決める。
- デモでは静的QR＋ローカル状態で演出し、本番ではサーバー検証へ差し替える。

## 5. ブースQRとスタンプ

### 5.1 証跡の定義

| 状態 | 証跡 | 意味 |
|---|---|---|
| 訪問した | ブース固有QR読取＋利用者の確定操作 | ブース付近でページを開き訪問を記録した |
| 説明を聞いた | 利用者のワンタップ申告 | 説明を聞いたと本人が回答した |
| 体験した | 利用者のワンタップ申告 | 体験したと本人が回答した |
| 購入した | 利用者のワンタップ申告 | 購入したと本人が回答した |
| スタッフ確認 | 将来のスタッフ操作／別QR | 出展者側で確認された。MVP外 |

自己申告を事実認定や売上実績として扱わない。レポートでは`来場者による回答`と明示する。

### 5.2 読取後画面

```text
┌──────────────────────────┐
│ [ブース画像]              │
│ ○○ブースにきたよ！         │
│ スタンプをゲットしました    │
│                          │
│ ここで何をした？ 複数選択可 │
│ [説明を聞いた] [体験した]   │
│ [購入した]    [まだ見学中]  │
│                          │
│ どうだった？（任意）        │
│ [😍][😊][😐][△]            │
│ [ひとことを書く________]    │
│                          │
│ [回答を送る] [あとで]       │
│                          │
│ [次のブースを探す]          │
└──────────────────────────┘
```

- スタンプは画面表示時ではなく、訪問確定API成功時に付与する。
- `あとで`を主操作と同程度に見つけやすくし、回答を強制しない。
- 感想は1タップ評価＋任意の短文。医療・健康に関する自由記述は公開せず、運営確認を経て扱う。
- `購入した`を押しても購入金額や商品名を自動推測しない。
- 同じブースの回答は後から追記・訂正できるが、履歴は監査用に保持する。

## 6. スタンプと報酬

- 初回ブース訪問でスタンプ1個。説明・体験・購入によって追加スタンプを与えない。
- 回答量を報酬へ直結させず、虚偽回答の誘因を作らない。
- 3ブース、5ブース等の回遊節目で演出やキャラクター表情を解放できる。
- 全ブース制覇を強く要求せず、混雑や子どもの疲労を優先する。
- 限定キャラクターは入口チェックイン報酬を基本とし、特定ブースへの不公平な誘導に使わない。

## 7. データイベント境界

詳細schemaを固定する前に、次の論理イベント境界を守る。

```text
event_checkin
  campaign_id
  occurred_at
  source = entrance_qr

booth_visit
  campaign_id
  booth_id
  occurred_at
  source = booth_qr

booth_engagement
  booth_visit_id
  action = heard_explanation | participated | purchased | browsing
  occurred_at
  証拠 = self_report

booth_feedback
  booth_visit_id
  rating
  comment_optional
  occurred_at

reward_grant
  campaign_id
  reward_id
  reason = event_checkin | booth_visit_milestone
  granted_at
```

- 同じ事実を複数テーブルで二重に正本化しない。
- すべての書込は冪等キーを持つ。
- QRにはLINE user ID、メール、連番の利用者IDを埋め込まない。
- QRは`campaign + booth + 署名またはサーバー解決用opaque token`だけを表す。
- 生LINE user IDは既存方針どおりHarness境界外へ出さない。
- 端末時刻だけを報告時刻の正にしない。受付時刻と端末発生時刻を分ける。

## 8. レポート

### 8.1 出展者向け

- ユニーク訪問者数
- 訪問者による`説明を聞いた／体験した／購入した`回答数と率
- 任意評価の分布
- 運営確認済みの感想抜粋
- 時間帯別の訪問傾向
- サンプル数とデータ定義

### 8.2 運営向け

- 事前プレイ → 会場チェックイン率
- チェックイン → 1ブース以上訪問率
- 訪問ブース数の分布
- ブース間の回遊。少数値・再識別リスクを抑えた集計に限定
- イベント後の再プレイ率
- QR読取失敗、重複、オフライン退避件数

### 8.3 表示しないもの

- 出展者への個人別来場者一覧
- 子どもの生まれ年月・性別と個別感想の組合せ
- 少人数セグメントで個人を推測できる集計
- 自己申告の購入を確定売上とする表示

## 9. デモのカットライン

今回のデモに含める:

- 入口チェックインQRの疑似読取またはデモボタン
- 当日限定キャラクターの付与演出
- 2〜3件の仮ブースQR導線
- スタンプ付与
- `説明を聞いた／体験した／購入した`の複数選択
- 1タップ評価、任意コメント、スキップ
- 利用者用スタンプ一覧
- 出展者レポートの仮集計画面
- イベント境界関数と計測点。永続DBへの本配線はしない

今回のデモに含めない:

- 本番用QRの一括発行・失効運用
- スタッフ確認
- 購入金額・決済連携
- 本番出展者への個人データ提供
- GPS、Bluetooth、Wi-Fiによる屋内追跡
- 商用価値のある報酬に対する不正防止

## 10. 本番移行Gate

1. 行動データ利用目的、同意文面、保持期間、削除方法の確定。
2. campaign、booth、QR token、イベント、報酬schemaのレビュー。
3. RLS、API認可、署名、冪等、レート制限、監査ログ。
4. QR流出・代理読取・再読取を含む不正利用の許容水準。
5. 出展者レポートの最小集計人数と少数値抑制。
6. 自由記述のモデレーション、問い合わせ、訂正対応。
7. 会場の通信障害を想定した端末キューと復旧テスト。
8. 出展者・運営・保護者・子どもによる実機テスト。

## 11. 成功指標

- 初回登録完了時間中央値60秒以内。
- 初回登録の画面別離脱率。
- QR起動からチェックイン完了まで10秒以内。
- ブースQR読取からスタンプ表示まで2秒以内。理想1秒以内。
- アンケートをスキップしても次のブースへ進める割合100%。
- 重複読取で二重報酬が発生しない。
- 出展者レポートですべての指標定義と自己申告区分を確認できる。

## 12. 参考にした現行原則

- Apple HIGのオンボーディング原則に従い、短く、体験に直結し、不要な設定は後回しにする。
- LINEのpermanent link／LIFF URLをブース別pathへ使い、印刷済みQRを継続利用できる構成とする。
- 行動データをLINEアカウントへ紐付ける場合は、利用目的を示して同意を記録する。
