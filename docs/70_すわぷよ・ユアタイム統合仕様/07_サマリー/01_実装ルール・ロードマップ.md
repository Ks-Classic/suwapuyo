# 実装ルール・ロードマップ

> 最終更新: 2026-07-19
> 開発エージェントへの実行時の正本: リポジトリルート`AGENTS.md`

## 1. 実装判断

全面書き直しはしない。ゲームコアと世界観資産を残し、入口・情報設計・保存境界・アクセシビリティを作り直す。

| 対象 | 判断 | 理由 |
|---|---|---|
| Pixi盤面・連鎖・音 | 再利用 | ゲーム価値が既にある |
| 村背景・キャラクター | 再利用・再編集 | ブランドDNA |
| 家族アンケート状態遷移 | 部分再利用 | 画面遷移の土台だけ残し、旧party・人数・性別・流入元・健康関係者ステップは削除 |
| 家族アンケート表示 | 全面リメイク | 汎用フォーム感が強い |
| 体操ホスト設定 | 再利用 | キャラと体操の対応がある |
| 体操画面・完了判定 | 作り直し | 待機だけで完了になる |
| `progressStore` | fallbackへ変更 | cloud SSoTではない |
| `track()` | 作り直し | 現在noop |
| スタンプ・ミッション演出 | 再利用 | 獲得体験の質が高い |
| 出展者レポート部品 | 再利用 | 集計の物語がある |
| レポートレイアウト | リファクタ | スクロール・密度・A11yに問題 |
| LINEデモメニュー・concierge | 削除済み | 現行MvpAppと正規URLへ統合し、旧デモを配信しない |
| `FuwafuwaDrawScreen` / `DigitalCanvas` | 部分再利用・全面再構成 | pointer描画は使えるが、3歳頃から小学生までの完成体験・描画補助・送信状態が不足 |
| `StaffPanel` / `RegisterForm` | 情報設計を作り直す | カメラ、画像、描画、同意、公開先、演出、作品管理が混在している |
| `DisplayScreen` / `FuwafuwaWorld` | 再利用・登場演出追加 | 表示エンジンを残し、タブレットから大画面への連続演出を追加 |

## 2. 先に解決する仕様矛盾

1. ゲーム・記録・会場マップ・ブース紹介を含む全利用者機能でLINE友だち追加を必須とする（決定-003）。公開Webの会場案内を作る場合は本仕様の改訂として別途起案し、現時点では例外を設けない。
2. 配信先はCloudflareを第一候補とし、旧Vercel記述を現行判断に使わない。
3. 既存の隠しキャラを廃止し、全キャラクターを常時見せる。アンケート完了で全キャラを一括登場させる（決定-019）。
4. `app_users`を中心にアンケート、ゲーム、体操、ブース接点を結ぶ。
5. 出展者レポートをデモに含めるが、サンプル値を実績と呼ばない。
6. 初回登録は`利用目的 → 誰が遊ぶか → 子どもの人数 → 全員の生まれ年・月と性別 → 確認`とする。年月と性別を継続保存し、遊び方は初回から外す（決定-031〜034）。
7. ブース紹介はアンケート個別最適化を行わず、体操テーマと公平ローテーションを使う。
8. 子ども用タブレット、PC中心・スマホ対応の運営管理、大画面表示を別責務にする。`/staff`へ子どもの描画UIを混在させない。
9. 決定-020の認証なし管理は集計閲覧デモだけに限定し、作品・ランド・設定の書込は要確認-007の運営認証確定まで本番公開しない。

## 5. UI実装ルール

- 1画面1主目的、主CTAは原則1つ。
- 絵文字を最終UI素材にしない。
- すべてを白い磨りガラスカードにしない。
- ゲーム中は盤面を第一階層にする。
- 長い画面はルート単位でスクロール可能にする。
- `body overflow:hidden`を全画面へ強制しない。
- オレンジ上の白文字など、基準未達の配色を使わない。
- タップ、フォーカス、disabled、loading、error、offlineを定義する。
- `aria-pressed`、`aria-expanded`、dialog focus、progress semanticsを実装する。
- reduced motionと音声オフを後付けにしない。
- 子ども用お絵描きに管理ナビ、カメラ、画像upload、同意、公開先を混在させない。
- 運営画面はPCを主対象とし、同じ機能をスマホの1カラムへ再配置する。PC版とスマホ版で別の業務ロジックを作らない。

## 6. データ実装ルール

- ブラウザから個人データtableへservice roleで直アクセスしない。
- LINEの生識別子を保存・表示・ログ出力しない。
- event UUIDで冪等にする。
- streakとmissionはサーバーを正とし、端末値を信用しない。
- unknownなevent name、property、survey answerを拒否する。
- D1とSupabaseの全同期を作らない。
- デモデータに`data_mode=demo`を持たせる。
- 作品の状態遷移と登場操作を冪等にし、PC・スマホの同時操作で二重登場させない。
- お絵描き中の設定を無断で即時変更せず、設定versionと適用セッションを持つ。

## 7. 外部連携実装ルール

- Webhookは署名→strict入力→永続dedupe→業務処理の順。
- request IDを入口から外部API・DBまで伝播する。
- child timeoutはparent SLAより3秒以上短くする。
- 一斉配信、DM、投稿は本番で人の承認を挟む。
- Harnessは検証済みtag/commitへ固定する。
- secretを`VITE_`環境変数へ置かない。

## 10. GPT/Codex開発モデルの使い分け

本節は開発作業の品質・速度・コストを調整するための運用であり、利用者向けアプリからGPT APIを呼び出す仕様ではない。具体的な永続指示は`AGENTS.md`を正とする。

| クラス | 主な担当 | 必須となる場面 |
|---|---|---|
| A: 最上位 | 設計、セキュリティ、プライバシー、DB、外部連携、SSoT矛盾解消、最終レビュー | 子どもデータ、認証・認可、本番設定、破壊的変更、公開前判断 |
| B: 標準 | 通常実装、UI、テスト、リファクタ、文書同期 | 原則の実装担当。A領域へ入ったら昇格 |
| C: 軽量 | 横断検索、一覧化、定型変換、一次整理 | 独立した機械的作業のみ。B以上の再確認必須 |

運用原則:

- モデル名を設計へ埋め込まず、利用可能な最上位・標準・軽量モデルへ読み替える。
- 現行候補はA=`gpt-5.6-sol`、B=`gpt-5.6-terra`、C=`gpt-5.6-luna`。選択画面で利用できない場合は同等クラスを使う。
- Cだけで仕様確定、完了判定、セキュリティ判断、本番反映を行わない。
- Aの判断も、要確認Gate、専門家監修、木幡さんの事業判断を代替しない。
- 並列化は独立した調査・ファイル・検証に限定し、共有状態や同一ファイルの競合を避ける。
- 作業完了時はセルフレビューと検証を行い、commit、push、Cloudflare deploy、LINE反映を個別に報告する。
