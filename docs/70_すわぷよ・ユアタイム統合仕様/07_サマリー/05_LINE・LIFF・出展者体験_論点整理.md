# LINE・LIFF・出展者体験 論点整理

> 状態: 2026-07-13の単一LIFF・公式アカウント中心設計を反映した作業台帳
> 目的: 決定済み・仮説・外部確認事項を分離し、1項目ずつ精査して正本へ反映する  
> 注意: 本書だけでDB migration、公開配信、画像転載を承認しない

## 1. 目標

すわぷよを単体ゲームで終わらせず、次の3つを同時に成立させる。

1. 利用者が迷わず遊び、キャラクターとYourTIME.を知り、イベント前後も戻りたくなる。
2. 全出展ブースを公平かつ魅力的に紹介し、来場・会場回遊・イベント後の再接点を増やす。
3. すわぷよ自体を制作実績として見せ、志と専門性を持つ出展者からツナヤスへの相談を生む。

北極星は単純なメニュータップ数ではなく、`遊ぶ → 知る → 会う／相談する → 戻る`が無理なくつながることである。

## 2. 対象者と期待する行動

| 対象 | 主目的 | 期待する次の行動 |
|---|---|---|
| 親子・一般来場者 | すわぷよを楽しみ、イベントを理解する | 再プレイ、ブース詳細閲覧、来場、出展者SNS閲覧 |
| 中高生等の単独利用者 | 保護者前提に固定されず遊べる | 初回設定、再プレイ、キャラとの接点 |
| 出展者 | 自ブースが丁寧に紹介され、制作の可能性を理解する | 課題別の相談、イベント後の面談 |
| YourTIME.運営 | 来場価値と出展価値を上げる | 情報更新、フェーズ切替、結果確認 |
| ツナヤス | 認知ではなく適合度の高い相談を得る | ヒアリング、提案、案件化 |

## 3. 体験全体像（2026-07-13決定）

```text
LINE公式アカウント（通常入口・再訪ホーム）
  └─ リッチメニュー
       ├─ すわぷよで遊ぶ ─────────→ 単一LIFF /
       ├─ YourTIME 出店ブース ────→ LINEキーワード応答
       ├─ YourTIME.日時・アクセス → LINEキーワード応答
       ├─ すわぷよって？ ─────────→ LINEキーワード応答
       └─ すわぷよの作り手 ───────→ LINEキーワード応答

作品固有QR（例外入口）
  └─ 単一LIFF /claim/{opaque_token}
       └─ 作品受取後は公式アカウントのリッチメニューへ合流
```

LINE公式アカウントを利用者にとっての固定ホームとする。旧会場案内所LIFFは別アプリとして維持せず、ゲーム、マップ、ブース、スタンプ、作品受取をすわぷよLIFF 1つのrouteへ統合する。LIFFログインは利用者へ独立した入口として見せず、個人状態を扱う画面の認証境界として使う。

通常入口は公式アカウントQR、作品受取だけは作品固有QRとする。この2種類は競合ではなく、一般・再訪・復旧と、個別作品claimを分担する。

## 4. 今回の決定

### 4.1 リッチメニュー

- Messaging APIで5枠の独自レイアウトを作る。
- 開催前、当日、開催後で内容を分ける。
- 開催前は次の5枠とする。
  - `すわぷよで遊ぶ`（最大領域）
  - `YourTIME 出店ブース`
  - `YourTIME.・日時／アクセス`
  - `すわぷよの作り手`
  - `すわぷよって？`
- 開催前の初回登録時点では、`すわぷよで遊ぶ`をLIFF URI action、5枠すべてをタップ可能にし、他4枠をmessage actionにする。
- `すわぷよって？`と`すわぷよの作り手`は短い絵文字付き説明をLINE上で返し、未確定URLは登録しない。
- ブース応答は確認済みカテゴリだけを絵文字と短文で紹介し、YourTIME.公式Instagram `https://www.instagram.com/your_time.niw/`へ誘導する。
- 日時・アクセス応答はYourTIME.の説明、開催日時、アクセス、申込・チケットURLを一組で返す。未確定値を推測しない。
- `ツナヤス`だけをラベルにせず、初見でも内容が分かる`すわぷよの作り手`を使う。
- AIデザイン体験ブースは出展ブースの1件であり、ツナヤス紹介枠とは分離する。

### 4.1.1 認証と友だち追加

- 通常利用者は公式アカウントを友だち追加し、リッチメニューをホームとして利用する。
- LINEログインは本人識別、友だち追加は通知・再訪、サービス同意は保存項目・利用目的の確認であり、相互に代替しない。
- 作品QRは同じLIFFの`/claim/{opaque_token}`へ入り、受取後に公式アカウントへ合流する。
- QRに作品IDやLINE user IDを直接入れず、一回限り・期限付き・失効可能なopaque tokenを使う。
- 作品claimの本番schema、署名、RLS、復旧はGate通過前に実装しない。

### 4.2 ブース紹介

- 全件カタログはLINEメッセージへ詰め込まず、LIFFの一覧・詳細ページで提供する。
- InstagramのYourTIME. 8thブース紹介投稿から26件を暫定候補として確認済み。
- 一覧では名称、画像、できること1行、カテゴリを優先する。
- 詳細では対象、所要時間、料金、予約要否、ブース番号、SNSを、確認済み情報だけ表示する。
- 表示順は公平にローテーションし、広告・協賛・運営枠は明示する。
- YourTIME.投稿画像のLIFF／LINE転載は、利用許諾または運営による利用範囲の確認後に公開する。
- 投稿画像のOCRや推測文言を公開用正本にしない。出展者名、表記、内容は投稿本文または出展者台帳で照合する。

### 4.3 会場マップ

- 端末GPSによる屋内現在地表示は実装しない。
- 正式会場図とブース番号の対応が得られるまで、位置を推測しない。
- 当日はブース詳細から会場図上のブース番号・エリアを強調する。
- 必要なら会場内QRで`いま見ているエリア`を手動更新できる余地を残すが、MVP必須にはしない。

### 4.4 ゲームのキャラクター4枠

- 初回は4枠を自動編成し、キャラクターとの偶発的な出会いを作る。
- 利用者は任意のキャラクターを選択できる。
- 手動選択を毎回上書きしないため、固定済み枠と未固定枠を分ける案を精査する。
- 新しいゲームでは未固定枠だけを再抽選し、`おまかせ編成`で全枠を再抽選できる案を第一候補とする。
- 単純な一様乱数ではなく、直近に登場していないキャラクターを少し優先し、認知の偏りを抑える。

### 4.5 `すわぷよの作り手`ページ

ページの最大目的はツナヤスの自己紹介ではなく、出展者が自分の課題を自分事化し、低負担で相談できることとする。

```text
いい活動が、ちゃんと届く仕組みをつくる
  ↓
すわぷよが生まれた背景と制作実例
  ↓
ツナマヨ: キャラクター、世界観、チラシ、キャラマーケティング
  ＋
やす: AI効率化、AI秘書、AI勉強会、AI／Webアプリ、Webサイト
  ↓
相談者の課題別入口
  ↓
LINE内で相談文を作り、会話を始める
```

課題別入口はサービス名ではなく次の3つを第一候補とする。

1. `もっと覚えてもらいたい`
2. `発信や仕事をラクにしたい`
3. `新しい体験をつくりたい`

ツナマヨの強みは`かわいい`だけでなく、認知、理解、記憶、共有、継続展開をつなぐキャラクター設計として説明する。やすの強みは`何でもできる`と羅列せず、相手の活動と業務課題を理解して、必要な仕組みを設計・実装・定着させることとして説明する。

CTA候補:

- `自分の活動でできることを聞く`
- `イベント後に少し話したい`
- `まず事例を見たい`

誇大な成果保証、人工的な希少性、本人が意図しない自動送信は用いない。

## 5. 開催フェーズ別の役割

| フェーズ | 利用者の中心課題 | リッチメニュー／LIFFの重点 |
|---|---|---|
| 開催前 | 何のイベントか、行く価値があるか | すわぷよ、全ブースの予習、日時・アクセス |
| 当日 | 次に何をするか、場所はどこか | 会場図、ブース番号、タイムテーブル、困ったとき |
| 開催後 | 楽しかった接点へ戻れるか | 再プレイ、出展者再訪、感想、次回案内 |

フェーズ切替は運営設定を正とし、端末時刻だけで勝手に切り替えない既存方針を維持する。

## 6. 計測の考え方

### 利用者体験

- リッチメニュー入口別タップ
- ブース一覧表示、詳細表示、カテゴリ変更、SNS遷移
- ゲーム開始、再プレイ、キャラクター選択、再抽選、固定
- イベント案内からアクセス情報を開いた回数

### 出展者価値

- 出展者別の表示資格回数、表示回数、詳細閲覧、外部遷移
- ローテーションの偏り
- `すわぷよの作り手`ページの課題選択
- 相談開始、面談化、提案化、案件化

相談開始以降は本人確認できる営業台帳で管理し、匿名の閲覧イベントと安易に結合しない。

## 7. 現行正本と衝突している重要事項

次の会話上の最新要望は、現行の決定-021〜028と衝突している。コード・DBへ進む前に最優先で正式決定する。

| 論点 | 現行正本 | 会話上の最新要望 | 影響 |
|---|---|---|---|
| 生まれ年・月 | 入力値は保存せず年齢帯だけ保存 | 初回後も生まれ年・月を保存 | 同意、DB、API、削除、再質問 |
| 複数児 | 詳細仕様の再確認が必要 | 初回に遊ぶ子ども全員を登録 | 初回質問数、家族モデル、編集UI |
| 性別 | MVPでは取得しない | 初回に子どもごとに取得・保存 | 選択肢、利用目的、分析境界、削除 |
| 遊び方質問 | 最大3問目として取得 | 何の話か分かりにくいため削除 | オンボーディング、体操初期選択 |
| 利用者 | 保護者中心 | 子ども単独・中高生も一応想定 | 同意、文言、年齢境界 |
| キャラ編成 | アンケート完了で全キャラ登場 | 4枠を毎回ランダム＋選択可能 | 保存状態、抽選、UI |

特に生まれ年・月と性別の保存は、実装都合で決めず、利用目的、表示文言、保存期間、編集・削除、複数児の識別方法を一組で決定する。2026-07-12時点で、初回に遊ぶ子ども全員を登録し、各子どもの生まれ年・月と性別を保存する方針は決定済みとする。

マーケティング活用を利用者へ隠さない。少なくとも次の境界を分ける。

- 基本同意: 年齢・性別に応じた体験調整、サービス改善、匿名または集計した利用傾向の分析。
- 別同意: 個人単位の広告ターゲティング、外部データとの突合、第三者提供、目的の異なる販促利用。
- 禁止: 子どもの不安や健康状態を推測した広告、診断・疾病リスクの推定、同意前の保存。

## 8. 外部確認が必要なGate

| Gate | 必要なもの | 未確認時の扱い |
|---|---|---|
| G-01 ブース正本 | 出展者名、紹介文、カテゴリ、料金、予約、SNS | 仮データ表示のみ |
| G-02 画像利用 | YourTIME.／出展者の画像利用範囲 | 公開環境へ転載しない |
| G-03 会場図 | 正式会場図、ブース番号、エリア | 一覧だけ提供し推測配置しない |
| G-04 ツナヤス素材 | やす・ツナマヨのキャラアイコン、プロフィール、実績 | プレースホルダーで構造だけ作る |
| G-05 相談先 | LINEトーク、フォーム、予約のどこへ送るか | CTAを外部送信しない |
| G-06 子ども情報 | 生まれ年・月・性別の選択肢、分析境界、同意文面 | DB migrationを行わない |

## 9. 精査と実装の順番

手戻りを最小化するため、次の順で1項目ずつ決定する。

1. **初回設定と保存境界**: 生まれ年・月、性別、複数児、単独利用、同意を確定する。
2. **情報設計**: 5枠リッチメニューと開催前／当日／開催後の遷移先を確定する。
3. **ブース台帳**: 26件を正規化し、公開可能な本文と画像を確認する。
4. **ブースLIFF**: 一覧、詳細、カテゴリ、会場図、外部CTAを設計・実装する。
5. **キャラ4枠**: 抽選、固定、選択、再抽選、計測を確定して実装する。
6. **作り手ページ**: ストーリー、課題別導線、相談CTA、計測を制作する。
7. **LINE運用**: リッチメニュー画像、エイリアス、フェーズ切替、Flex配信を設定する。
8. **実機検証**: LIFF、LINE内ブラウザ、アクセシビリティ、公平性、計測を確認する。

各項目は`目的 → 対象 → 成功条件 → 画面 → データ → 計測 → 失敗時 → テスト`の順でセルフレビューし、決定後に要件、UI、API、DB、テストへ同期する。

## 10. 最初に精査する項目

最初は`初回設定と保存境界`とする。これは後続の画面、DB、利用目的文、年齢別体験、複数児切替に直接影響し、後から変えると最も手戻りが大きいためである。

確定すべき問い:

1. 生まれ年・月と性別を、体験調整、サービス改善、集計分析のどこまで基本同意で利用するか。
2. 性別の選択肢を`女の子／男の子／その他・答えたくない`とするか。表示順や表現をどうするか。
3. 初回に全員登録しても離脱を増やさない、追加・確認・完了UIをどうするか。
4. 複数児をどう区別するか。名前を取らず`1人目／2人目`またはニックネーム任意にするか。
5. 子ども単独利用時に保護者同意を必須にする年齢境界と確認方法をどうするか。
6. 閲覧・編集・削除をどこから行えるようにするか。

## 11. 初回同意UIと実文面

LINE友だち追加とLIFF認可だけを、すわぷよによる子ども情報の保存・分析への同意として扱わない。初回LIFF起動後、子ども情報を入力・保存する前に、サービス側の確認画面を1回表示する。

### 11.1 初期画面

```text
┌──────────────────────────┐
│         [わーわー]         │
│                          │
│  みんなで遊びやすくするために │
│                          │
│  遊ぶお子さんの生まれた年月、 │
│  性別、遊んだ記録を保存します。│
│                          │
│  ・年齢に合わせた表示         │
│  ・サービスの改善             │
│  ・利用傾向の集計と分析       │
│  に使います。                │
│                          │
│ [利用規約] [プライバシー]     │
│                          │
│ [ 内容を確認してはじめる ]     │
│ [ 今はやめておく ]            │
└──────────────────────────┘
```

画面文面:

- 見出し: `みんなで遊びやすくするために`
- 本文: `遊ぶお子さんの生まれた年月、性別、遊んだ記録を保存します。年齢に合わせた表示、サービスの改善、利用傾向の集計と分析に使います。`
- 補足: `登録した情報は、あとから確認・変更・削除できます。`
- 主CTA: `内容を確認してはじめる`
- 副CTA: `今はやめておく`
- リンク: `利用規約`、`プライバシーポリシー`

`マーケティングのため`だけで済ませず、何を分析し、何に使うかを利用者が予測できる粒度で示す。過度に幼い文体、過剰な不安喚起、同意ボタンだけを強くして拒否を隠すダークパターンを使わない。

### 11.2 子ども登録画面

- 見出し: `いっしょに遊ぶお子さんを登録してね`
- 説明: `遊ぶお子さん全員について教えてください。ひとりずつ、遊びやすい表示に整えます。`
- カード見出し: `1人目`、`2人目`。識別名は初期段階では番号とし、ニックネームは別判断。
- 項目: `生まれた年`、`生まれた月`、`性別`
- 追加CTA: `＋ もうひとり追加`
- 完了CTA: `この内容ではじめる`
- 確認: `○人のお子さんを登録します`

性別は無回答状態のまま完了させず、`答えたくない`を明示的な有効回答として用意する。これにより入力漏れと回答拒否を分析上区別する。

### 11.3 同意記録

保存する同意記録:

- `consent_type`
- `terms_version`
- `privacy_version`
- `purpose_version`
- `accepted_at`
- `actor_type`（本人／保護者等。実装前に選択肢を固定）
- `source`（LIFF初回、設定変更等）

利用目的の変更時は、軽微な文言修正と実質的な目的追加を区別する。個人別販促、第三者提供、外部データ突合などの目的追加は再同意を必須とする。

### 11.4 マーケティング利用の境界

| 利用 | 初回基本確認 | 追加同意 |
|---|---:|---:|
| 年齢に応じた表示 | 含む | 不要 |
| プレイ・体操記録の保存 | 含む | 不要 |
| 年齢・性別・行動の集計分析 | 含む | 不要 |
| サービスやイベント内容の改善 | 含む | 不要 |
| 自社サービスの一般的な案内 | 利用目的へ具体的に記載 | 配信内容に応じて停止手段を提供 |
| 属性・行動に基づく個別販促 | 含めない | 必須 |
| 出展者等への個人データ提供 | 含めない | 必須 |
| 外部データとの個人単位の突合 | 含めない | 必須 |

匿名または集計済みの出展者レポートは、再識別できない最小人数基準と少数値抑制を別途定義する。子どもの健康状態、疾病リスク、不安を推測した販促は行わない。
