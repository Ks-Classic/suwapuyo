## 3. 実装前に回答が必要

### 要確認-001 性別の回答対象 → 方針更新（2026-07-11）

決定-016・025は決定-031で上書きした。MVPでは初回に子どもごとに性別を取得・保存する。選択肢と利用目的は要確認-011で固定する。

### 要確認-002 アンケート完了後のキャラクター登場単位 → 決定済み（2026-07-11）

A（全キャラクター一括登場）で確定。決定-019へ昇格。

### 要確認-003 自動体操提案の間隔 → 決定済み（2026-07-11）

B（60秒）で確定。決定-017へ昇格。実機検証で違和感があれば設定値として調整する。

### 要確認-004 長期保持の具体期間 → 決定済み（2026-07-11）

無期限保持（アカウント有効な間）で確定。決定-018へ昇格。削除依頼・同意撤回・バックアップ世代失効の扱いをプライバシーポリシーへ明記する。

### 要確認-005 興味カテゴリ

出展者台帳と会場カテゴリ確定後に選択肢を固定する。自由入力は採用しない。

### 要確認-006 会場図とブース位置

正式な会場図、ブース番号、出展者ID、座標の対応表が必要。対応表がない状態で推測配置しない。

### 要確認-007 出展者・運営の認証方式

MVPの集計閲覧デモは認証なしで運用できる（決定-020。集計値のみ・UUIDパス・書込系API非公開が成立条件）。作品公開、非表示、ランド操作、お絵描き設定等をPC・スマホから書き込む前に方式を確定する。

- A: Supabase Authのmagic link。
- B: Cloudflare Access。
- C: パスワード＋2FA。

いずれもfail-closed（未設定時は全拒否）を必須条件とする。

### 要確認-008 実装フェーズの日程確定

`07_サマリー/01`の日程（8/2逆算・仮決定）と外部Gate期日を、着手前に実稼働可能日と突き合わせて確定する。

### 要確認-009 年齢帯別体操ルールの監修

年齢帯ごとの対象体操、説明文、回数、姿勢、安全上の注意を体操コンテンツ単位で監修し、version付きルールとして固定する。監修前はデモ表示に限定し、`その子に合う`、`改善する`等の表現を公開しない。

### 要確認-010 初回質問・イベント質問のDB/API前提

2026-07-12に決定-026〜030として確定。詳細と実装Gateは`04_初回質問・イベント質問_実装前設計監査.md`を正とする。

- 生まれ年pickerの対象上限。
- `からだ` / `おまかせ`の初回体操決定と固定期間。
- 生まれ年・月の継続保存に伴う年齢帯更新。旧`保存しない`前提は決定-032で廃止。
- イベント回答の同意単位と保持期間。
- イベントphaseの決定元、JST切替境界、設定不正時のfallback。

### 要確認-011 子どもの性別・生まれ年月・複数児の保存境界

2026-07-12に、性別と生まれ年・月を子どもごとに継続保存し、初回に遊ぶ子ども全員を登録する方針を決定した。DB/API変更前に次を固定する。

- 性別の選択肢と`答えたくない`の扱い。
- 体験調整、サービス改善、集計分析、個人単位マーケティングの同意境界。
- 複数児の識別方法。氏名は取得せず、番号表示または任意ニックネームを候補とする。
- 本人・保護者による閲覧、編集、子ども単位の削除。
- 子ども単独利用時の同意フロー。

### 要確認-012 当日お絵描きの回転率・描画補助・登場演出

3歳頃から小学生までの実機テストで次を確定する。短時間で回す方針は確定だが、数値・種類を推測で固定しない。

- 1人あたりのお絵描き開始から完成までの目標・上限時間。
- 土台テンプレート、目・口等のスタンプ、色数、初期線幅の採否と種類。
- 完成率、描き直し率、スタッフ介入回数の合格基準。
- 登場演出のパターン数、尺、効果音、次の子を開始できるタイミング。

### 要確認-013 当日端末の同期・復旧方式

現行はSupabase Storage / Postgres / Realtimeを第一、IndexedDBを表示キャッシュ・復旧用としている。会場回線断でも新規作品をタブレットから表示PCへ渡す要件をどこまで満たすかを確定する。

- A: クラウド第一。回線断中はタブレットに未送信保存し、表示済みランドだけ継続する。
- B: Aに加えて、同一PC内または会場LANのローカル同期を用意する。
- C: 予備導線として表示PC上のお絵描きへ切り替える。

採用方式、復旧手順、必要機材、対象ブラウザを本番テスト前に固定する。運営書込認証は要確認-007を前提とする。

## 4. 未確定事項の実装ルール

- `要確認`を開発者判断で確定へ変えない。
- UIデモが必要な場合は`data_mode=demo`と仮値ラベルを表示する。
- DB migration、公開文言、外部配信へ未確定値を入れない。
- 決定後は本ファイル、要件、UI、API、DB、テストを同時更新する。
